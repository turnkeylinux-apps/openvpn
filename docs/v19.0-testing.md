# OpenVPN 19.0 testing

## Scope and source decision

OpenVPN 19.0 uses Debian 13 Trixie packages for OpenVPN Community Edition,
Easy-RSA, iptables and their supporting libraries. Debian supplies the complete
application stack, so this appliance adds no third-party application
repository or downloaded application artifact. The inherited TurnKey Core and
Webmin packages continue to use the signed TurnKey Trixie repository.

The OpenVPN, Easy-RSA and iptables update path is normal authenticated APT.
`tests/v19.sh` refreshes signed metadata, confirms an eligible candidate for
each identity-defining package, and proves that the nonmutating check did not
change installed versions. No separate compatible apply fixture exists or is
needed for the Debian package route.

The acceptance command is:

```sh
TKLDEV_CONTAINER=tkldev19-jeremy-qa \
TKL_HARNESS_STATE_DIR=/home/agent/.local/state/jeremy-v19-pr-qa/openvpn \
TKL_HARNESS_LOCK_FILE=/home/agent/.local/state/jeremy-v19-pr-qa/build.lock \
/home/agent/turnkey/tools/test-v19-appliance openvpn \
  --source /home/agent/.local/state/jeremy-v19-pr-qa/worktrees/openvpn-candidate
```

It builds a configured Trixie root in TKLDev, imports it into a disposable
privileged Docker container, follows normal systemd init and firstboot, and
runs `tests/v19.sh`. The retained harness report records the exact source and
harness commits, source archive/tree hashes, configured-root driver, runtime
evidence, updater evidence, cleanup status and verdict.

## Security and failure boundaries

- Firstboot administrator inputs cross into Easy-RSA variables and OpenVPN
  configuration. The Python hook validates email, DNS/IP address and strict
  IPv4 networks before changing PKI; the shell initializer independently
  rejects unsafe email/address spellings. Failed initialization or service
  restart is fatal rather than silently leaving partial success.
- Client names cross into certificate and filesystem paths. The helper scripts
  accept only a bounded portable name, validate email, subnet and port values,
  and create embedded-private-key profiles and keys with mode `0600` under a
  process umask of `0077`.
- The kernel routing table selects the current IPv4 default interface. The
  dedicated oneshot helper validates that kernel-provided name, installs one
  idempotent, appliance-labelled rule limited to the configured VPN subnet,
  records it below `/run`, and removes that exact rule on stop. No interface
  name such as `eth0` is assumed.
- OpenVPN starts as root only for device, socket and key setup, then follows
  the shipped configuration's `user nobody`, `group nogroup` and CRL chroot.
  The NAT service is bounded to `CAP_NET_ADMIN` and the `CAP_NET_RAW` socket
  capability required by iptables-legacy, a read-only system tree and its one
  `/run` state file.

The server profile's optional routed private LAN and the client profile's
site-to-site routing use the same validated CIDR and authenticated tunnel
primitives. Acceptance exercises the higher-value gateway path end to end; it
does not create a second physical LAN solely to duplicate those primitives.

## Known limitations and deferred work

The Docker path does not exercise the installer, host kernel variants,
physical interfaces, cloud security groups or mobile QR scanners. The test
does exercise privileged TUN creation, a separate client network namespace,
certificate authentication, real encrypted data transfer, forwarding, NAT and
service restart. The inherited Core 19 baseline covers unchanged platform
behavior.

IPv6 enablement remains explicitly documented as future, untested work in
`docs/ipv6.md`; it is not a v19.0 runtime claim. Performance, multi-client load,
optional TLS 1.3-only configuration and exhaustive site-to-site topology
coverage are outside the functional 20/80 gate.
